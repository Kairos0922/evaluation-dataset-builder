# 用例判定契约规范

## 选择判定方式

根据用例需要测量的结果选择判定方式：规则检查用于固定标签、Schema、数值和明确约束；参考结果比对仅在存在可信预期结果时使用；量表用于表达形式开放但可定义评价维度的回答；状态检查用于验证 Agent 修改文件、调用接口或改变环境后的真实结果；执行轨迹检查用于检查流程约束、工具调用和禁止操作；人工审查用于必须由责任人判断的复杂或高影响结果；混合方式用于包含多个不同判定维度的结果。

判定方式属于用例内部的判定契约。应按任务、能力和证据条件选择，不得为所有用例强制使用同一种方式，也不要求生成独立评分器、评分器注册表或可部署的判定服务。

## 必备定义

每条用例必须说明判定目标、适用方法、判定项、必须观察的证据、通过条件、失败条件、可接受的结果变体，以及 UNKNOWN 的处理方式。使用参考结果时，还必须记录参考来源及其权威性。只有任务确实需要部分得分时，才定义部分得分规则。

## 判定原则

对结构化和受约束的结果，优先使用确定性检查。只有存在可信参考结果时，才进行参考结果比对。不得对允许多种合理表达的自然语言回答进行无依据的逐字匹配。

对会改变文件、资源、权限或外部系统状态的 Agent，必须检查实际终态和副作用。对工具使用过程有要求时，必须检查实际执行轨迹，不能只依据最终文字。

当关键证据缺失、格式错误、存在歧义或无法核验时，必须判为 UNKNOWN 或按规则阻断，不得判为通过。不得将未执行的状态检查或轨迹检查描述为已验证。

## 判定契约审查

## 先明确被评分主体，防止把被测系统缺陷判成 Agent 失败

编写每条用例前，必须明确 `evaluation_subject`：本次究竟在评价被测应用/API 本身，还是评价一个负责测试、审计、诊断或发现缺陷的 Agent/Skill。

- 当评测对象是测试型 Agent/Skill 时，应用是否符合业务规则属于**被观察对象的实际状态**，不是自动等同于 Agent/Skill 的得分。若应用存在缺陷，Agent/Skill 准确执行测试、观察到差异、如实报告 FAIL 并提供充分证据，应按评测目标判为 Agent/Skill 表现正确（PASS）。
- 此时每个 criterion 的 `pass_condition` / `fail_condition` 必须描述 Agent/Skill 的行为、判断和证据质量。例如，“观察到结果为空，并正确指出其违反 BR-02”可以是通过条件；“应用返回空结果”本身不能单独作为 Agent/Skill 的失败条件。
- 当评测对象是应用/API 本身时，应用实际违反业务规则可以是 FAIL。不得把这套规则机械套用到不同的评测主体。
- 不得在同一 criterion 中混用“被测系统是否符合规则”和“Agent/Skill 是否正确发现并报告偏差”两个层级。若用例同时测量二者，必须拆成独立判定项，并明确各自的评分主体及合成规则。
- 集中审查时，将 case-level `pass_conditions`、`fail_conditions` 与每个 criterion 的通过/失败条件逐项对照。若 case-level 明确允许“观察到缺陷并如实报告 FAIL”获得通过，任何 criterion 都不得仅因观察到该缺陷就判 Agent/Skill 失败。
- **逐分支区分应用偏差与 Agent/Skill 失误。** 当应用实际状态可能与预期不一致时，criterion 的 `pass_condition` 应允许 Agent/Skill 准确报告该实际状态及相应规则偏差；`fail_condition` 只能描述 Agent/Skill 漏检、误报、报告值与实际证据不一致、遗漏关键步骤、违反执行契约或证据不足。不得把“状态/按钮/摘要/优先级与预期不一致”或“应用返回空结果”单独作为测试型 Agent/Skill 的失败条件。若应用状态与 Skill 报告值不一致，必须明确写成“Skill 报告值与同一步 DOM/响应/轨迹证据不一致”。



质量审查应验证判定项是否对应评测目标，条件是否明确、可观察且相互一致，证据是否可获得，合理变体是否被处理，UNKNOWN 是否安全失败。正例、负例、边界例和对抗例是可选的评测场景类型；仅在覆盖目标需要时纳入，不将其默认视为独立校准集。

判定规则或预期结果发生变化时，识别受影响用例并重新审查判定契约的一致性。高影响用途可增加独立人工复核，但不得将其描述为已执行的自动校准。

## Agent、Skill 与工具轨迹判定

当评测目标涉及工具调用、API 操作、多步工作流或状态变更时，除最终回答外，应按适用性检查真实可观察轨迹：必需/禁止工具、调用顺序、参数约束、步骤上限、关键事件、状态变化、错误处理和副作用。只在任务要求这些行为且宿主环境提供相应证据时启用；不得要求所有任务都具有工具轨迹。

轨迹断言必须区分“过程约束”和“结果约束”。最终结果正确不能抵消越权、禁止工具调用或不安全副作用；过程合规也不能替代结果正确。缺少实际轨迹时判为 UNKNOWN 或 NOT_RUN，不得根据 Agent 的文字自述推定工具已成功执行。
