# 变更影响分析与局部修复规范

## 目的
当业务规则、来源、系统能力、评分器或评测目标变化时，识别受影响资产并进行最小充分修复，避免无差别重建整个数据集。

## 依赖关系
维护以下可追溯关系：
来源/版本 → 业务规则或能力 → 业务场景/状态转换 → 用例 → 评分器/断言 → 覆盖统计与报告。
每个节点使用稳定标识。无法建立精确关联时，记录采用的保守影响范围和判断理由。

## 变更记录
每次变更至少记录：
- change_id、变更类型、发现时间和来源；
- 旧版本、新版本、生效日期及精确差异；
- 受影响规则、能力、场景、用例和评分器标识；
- 影响判定依据、影响等级和不确定性；
- 需要执行的核验、修复、重测和重新校准动作；
- 变更前后覆盖差异；
- 当前状态和验证证据。

## 局部修复流程
1. 核实变更来源及权威性；未经核实的报告不得直接覆盖已确认规则。
2. 沿依赖关系识别直接受影响资产，再检查相关边界、冲突和依赖场景。
3. 将资产分类为：保持不变、需要更新、需要新增、需要废弃、需要重新核验。
4. 只修改受影响的用例和评分器，保留不受影响的稳定 ID。
5. 对修复内容重新执行适用的结构、证据、可判定性、去重和覆盖检查。
6. 若评分规则或预期结果变化，重新校准受影响评分器。
7. 更新覆盖矩阵、来源映射、版本和变更日志；记录需要真实执行的回归范围。
8. 未实际完成的核验或执行标记为 RERUN_REQUIRED / NOT_RUN，不得标记通过。

## 影响范围不足时
若来源无法定位到规则或场景，扩大检查范围并明确说明原因；不得假装依赖关系完整。若变更存在未解决冲突，将受影响金标准和用例标记为 needs_info，暂停批准，但继续处理不受影响部分。
