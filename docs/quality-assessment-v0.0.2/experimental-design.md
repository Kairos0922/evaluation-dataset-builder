# v0.0.2 公式验证实验设计

**状态：** 实验设计草案；尚未收集验证样本、专家评分或真实运行结果。  
**目的：** 把“公式有效”转化为可证伪、可复现的经验主张。

## 1. 实验总体结构

采用多阶段验证，避免用同一批专家标签既设计指标又证明指标有效。

| 阶段 | 目标 | 数据 | 主要结果 |
|---|---|---|---|
| E0 构念定义 | 确定评价对象、用途和解释边界 | 文献、用户需求、领域任务模型 | 构念蓝图 |
| E1 内容验证 | 检查指标是否覆盖且适配构念 | 独立专家盲评、定性反馈 | CVI/CVR/Aiken's V、分歧 |
| E2 评分过程验证 | 检查审查者/Judge是否按规则评分 | 训练样例、think-aloud、重复盲评 | 一致性、误解模式 |
| E3 缺陷识别实验 | 检查离线指标能否识别已知数据集缺陷 | 基线数据集及受控缺陷变体 | 缺陷类别级检出和误报 |
| E4 运行效标实验 | 检查离线指标是否关联真实测量效力 | 真实 Agent/Skill 运行、Oracle、历史缺陷 | 预测效度和误差区间 |
| E5 模型开发 | 比较公式族并估计候选参数 | 开发数据集 | 内部交叉验证结果 |
| E6 冻结验证 | 在从未参与开发的数据上检验模型 | 锁定验证集 | 确认性效度、校准和稳健性 |
| E7 外部复现 | 检查跨 Agent/Skill、领域、模型和环境的泛化 | 独立来源/团队/环境 | 适用范围声明 |

## 2. 参考样本构成

不能只使用由 Builder 自己生成的数据集来验证 Builder 的质量评分器，否则会产生来源偏差和自我验证循环。

候选来源应包括：
- 已公开且具有任务、Oracle/Verifier 和文档的 Agent Benchmark；
- 不同团队、不同 Agent/Skill 类型构建的真实评测集；
- 有明确历史缺陷和修订记录的 Regression 套件；
- Builder 生成的真实数据集，但需与独立外部样本分开报告；
- 对真实基线样本做的受控缺陷变体。

每份数据集需要记录来源许可、版本、SHA-256、任务领域、目标能力、用途、工具/环境依赖、评分器类型和已知限制。

## 3. 样本量与统计功效

不预先规定“至少 N 个数据集/用例/专家/运行”作为普遍门槛。

样本量规划步骤：
1. 先明确主要效标和主要统计假设。
2. 明确最小有意义效应（smallest effect size of interest）或可接受的错误风险。
3. 使用小规模 Pilot 估计基率、方差、评审者分歧、任务内相关和数据集间异质性。
4. 对拟合的多层/配对模型进行模拟功效分析，考虑数据集聚类、任务嵌套、重复运行和不平衡样本。
5. 以置信区间宽度、参数估计误差、决策错误率和成本共同判断样本是否充分。
6. 将假设、分析和停止规则在确认性验证前冻结。

若样本不足，报告“统计证据不足”，不得用经验门槛替代功效分析。

## 4. 专家盲评设计

### 4.1 专家任务

专家分别评估：
- 指标是否相关、必要、可观察、可操作；
- 用例是否测量声明的构念；
- Ground Truth / Rubric 是否正确且完整；
- 关键缺陷是否会改变数据集的用途适配性；
- 是否存在无法由当前指标捕捉的重要缺陷。

### 4.2 防偏差设计

- 专家不知道数据集由哪个 Builder/团队生成。
- 专家不知道候选总分、自动评分和其他专家的结论。
- 同一评审批次混入无缺陷控制样本和缺陷变体。
- 任务顺序随机化；必要时进行重复样本检查。
- 对有争议的项目保留多种合理判断，不能强行把分歧抹平。
- 记录专家背景、利益冲突、培训、指导文件版本和评审时间。

### 4.3 统计报告

按评分尺度报告原始分布、分歧矩阵和适用的一致性系数。对相关性/必要性/构念覆盖分别选择 CVI、CVR、Aiken's V 或其他方法。不能只给一个汇总系数。

## 5. 缺陷注入实验

### 5.1 缺陷族

至少覆盖：
- 目标构念偏离或无关能力主导；
- 任务描述歧义或不可解；
- Ground Truth 错误/来源伪造/引用错配；
- Rubric 漏项、目标主体错配或证据不可观察；
- 评分器漏洞、对空输出误判、字符串脆弱匹配；
- 关键能力/风险覆盖缺失；
- 近重复和测量信息冗余；
- 数据污染或答案泄漏；
- 执行环境、工具、权限和清理要求不完整。

### 5.2 实验控制

- 每次注入尽量只改变一个缺陷因素。
- 为每种变体保留原始基线和变异说明。
- 由独立审查确认变异确实引入目标缺陷，排除等价变异。
- 评审者/评价器不获知变异类型。
- 同时加入无缺陷的无关编辑，检查评价器是否误报。
- 对多缺陷组合另设实验，不与单缺陷实验混淆。

### 5.3 报告

按缺陷类型和严重度报告召回、误报、混淆矩阵、区间和错误案例。不能只报告总体准确率，因为缺陷基率与类别分布会影响解释。

## 6. 真实运行效标实验

### 6.1 通用控制

- 固定数据集 SHA、Agent/Skill SHA、模型 ID、Harness、提示、工具版本、环境快照和执行协议。
- 区分有效运行、环境失败、Agent 失败、Judge 失败和 UNKNOWN。
- 同一轨迹可被不同 Judge 独立评分，分离 Judge 误差。
- 通过随机种子和重复运行估计 Agent 随机性；通过环境健康检查估计基础设施波动。
- 使用独立 Oracle 或经专家裁定的标签，不让被测 Agent/Judge 生成自己的唯一金标准。

### 6.2 Capability 实验

- 选择有能力差异的 Agent/模型/配置，但记录能力总体的抽样边界。
- 尽可能让多个 Agent 完成同一任务集，构成可分析的响应矩阵。
- 对适用模型检查 IRT 参数、模型拟合、局部独立和 DIF。
- 对 Agent × Task × Seed × Environment × Rater 设计使用 G-Theory 或层级模型分解误差。
- 将能力估计与独立任务/已知组结果比较。
- 分析数据集在不同能力区间的信息量，而不是只看总体准确率。

### 6.3 Regression 实验

- 对旧版本和新版本使用同一任务、相同环境和配对协议。
- 用已确认的历史缺陷进行回放。
- 注入非等价变异缺陷，另行报告变异检出。
- 对关键权限、安全和副作用约束设置单独的非补偿判定。
- 报告新旧版本任务级转移矩阵、配对差异、McNemar/Bootstrap 区间和 Flakiness。
- 分开测量“发现故障”和“暴露可观察失败”。

## 7. 候选公式开发与冻结验证

### 7.1 开发阶段

- 指标锚点和归一化方法先由定义和内容效度证据建立。
- 仅在开发集上比较门禁画像、算术、几何、瓶颈和用途专属模型。
- 若采用数据驱动权重，必须通过嵌套分组交叉验证，防止同一数据集/来源家族跨折泄漏。
- 复杂模型必须证明相对简单模型有增量价值。
- 记录模型搜索空间和所有尝试，避免只发布最优结果而隐藏失败尝试。

### 7.2 锁定验证

在锁定验证集上仅执行冻结模型：
- 预测效度；
- 校准；
- 已知缺陷识别；
- 错误放行/误拒绝；
- 排序/决策稳定性；
- 权重与标准化敏感性；
- 分领域、分 Agent/Skill 和分用途表现。

锁定验证失败后，模型修订需要新的独立验证集；不能反复在同一锁定集上调参并仍称其为独立验证。

## 8. 通过/不通过解释

不预设单一数字阈值。确认性实验开始前，必须依据决策用途、错误代价、效标基率和可接受不确定性，冻结：
- 主要效标；
- 主要统计量；
- 置信区间方法；
- 最小有意义效应；
- 误放行/误拒绝成本；
- 多重比较处理；
- 停止规则；
- 适用范围。

若证据不足、模型不稳定或无法跨域泛化，结论为 PARTIALLY_VALIDATED 或 NOT_VALIDATED，并保留分项画像。

## 9. 实验交付

每轮实验必须归档：
- 预注册协议及 SHA；
- 数据集清单、数据切分与 SHA；
- 原始专家评分和匿名化信息；
- 变异算子及变异确认记录；
- Agent/Skill/模型/环境/工具精确版本；
- 原始轨迹、Oracle 和 Judge 结果；
- 统计分析脚本、依赖版本和运行日志；
- 报告、限制、失败案例和修订决策。

## 9. 已知缺陷注入目录与测试边界

受控缺陷类别和预期信号集中记录在 [defect-mutation-catalog.yaml](defect-mutation-catalog.yaml)。

- IDA-M01–M08：确定性结构、身份、来源注册表、精确重复和覆盖声明缺陷。
- IDA-M09–M12：歧义、错误 Ground Truth、构念错配和答案泄漏。这些不能由当前结构检查器证明，需要 Oracle、专家或污染审计。
- ERA-M01–M08：Judge false pass / false fail / abstention、配对回归、历史故障、变异缺陷、重复运行不一致和失败暴露。

当前单元测试覆盖这些确定性信号中的一部分，并持续扩充。通过注入测试只证明“实现能对预先编码的缺陷产生预期信号”，不证明缺陷目录完整，也不证明质量公式对真实数据有效。正式公式验证仍需盲测缺陷、独立专家标签和外部效标。
